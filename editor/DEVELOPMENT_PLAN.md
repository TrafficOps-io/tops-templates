# План развития Landing Studio и ИИ ассистента

> Примечание: разделы о хранении проектов заменены документом `docs/superpowers/specs/2026-10-02-folder-first-storage-design.md` (папка проекта как единственное хранилище).

Дата: 1 октября 2026 года. Статус: предложение к реализации. Основа: скриншоты пользователя и текущая рабочая копия `editor`, `template-editor-shell` и `template-editor-core`, включая незакоммиченные доработки редактирования отдельных файлов. Поведение развёрнутой версии отдельно не проверялось.

Цель — сделать проект постоянным рабочим пространством с несколькими диалогами ИИ, историей и независимыми черновиками. Ручное редактирование, автосохранение и переход между проектами должны работать во время генерации. Проект должен сохранять идентичность и диалоги при переходе из библиотеки Studio в папку на компьютере.

Пользователь выбрал применение изменений **после просмотра**: каждый диалог готовит свой черновик, редактор остаётся доступным. Это базовое требование всех этапов ниже.

## Основные решения

1. Один лендинг или шаблон — один проект со стабильным `projectId`. Папка является местом его хранения, а не отдельным типом проекта.
2. В проекте доступны несколько диалогов. Сообщения, вложения, выполнение запросов и черновики принадлежат конкретному диалогу.
3. Новый диалог начинается с одного поля ввода, вложений и упоминаний файлов. Submit сохраняет сообщение, создаёт диалог и открывает его.
4. Выбор `Edit project / Fill content` убирается из обязательного пользовательского сценария. Ассистент выбирает нужные инструменты по запросу. Явное ограничение «только контент» или «только этот файл» остаётся обязательным для исполнения.
5. ИИ работает с отдельной копией исходного состояния. Его результат не замещает текущие файлы редактора и не останавливает автосохранение.
6. Пользователь просматривает изменения и применяет их к актуальному проекту. Устаревший результат нельзя записать поверх ручных правок или результата другого диалога.
7. В установленном PWA редактор — постоянный экран приложения. Компактный и развёрнутый режимы остаются у встроенного редактора.
8. Одно меню «Экспорт» предлагает лендинг для хостинга и переносимый проект Studio. «Сохранить в папку» меняет хранение существующего проекта.

Предлагается сохранить текущую локальную архитектуру и BYOK. Облачная синхронизация, серверное выполнение после закрытия приложения, Git worktrees и командная работа в этот объём не входят. Ограничение AI и прямого доступа к папкам установленным PWA пока сохраняется как политика Studio.

Существующие локальные draft copies, независимые planner/reviewer, валидация парсером и renderer, контроль revision и сохранение только завершённых файлов следует переиспользовать. Новую систему нельзя строить простым удалением `locked` и проверки `active`: нынешнее применение заменяет весь `files` object и потеряет параллельные правки.

## Структура рабочего пространства

Верхняя панель содержит выбор проекта, его название, статус сохранения, «Хранение проекта», «Экспорт» и настройки ИИ. Слева — диалоги выбранного проекта с кнопкой «Новый диалог», а также доступ к файлам и контенту. Основная область показывает диалог, исходник или контент. Справа можно открыть preview текущего проекта либо выбранного черновика.

Первичная навигация — проекты; диалоги всегда принадлежат выбранному проекту. В дереве файлов остаются действия с файлами: создать, загрузить, переименовать, удалить. Открытие проекта, импорт ZIP и подключение папки переносятся на уровень проекта.

Диалог в списке показывает название и состояние: «В очереди», «Работает», «Изменения готовы», «Нужна помощь». Доступны переименование, архивирование и поиск по названиям и сообщениям. Архивирование сохраняет историю; активное выполнение архивированием не отменяется. Завершение запроса в другом проекте отображается в навигации без принудительного переключения экрана.

Показанные в скриншотах термины `Library`, `New`, `OpenRouter`, `Project folders` требуют понятных подписей по смыслу. В английской локали это соответственно `Projects`, `New project`, `AI settings`, `Project storage`; переводы добавляются через существующий механизм локализации. Иконки дополняют подписи. Tooltip помогает уточнить действие, но не заменяет видимое название важной кнопки.

## Начало и продолжение диалога

### Новый диалог в существующем проекте

Стартовый экран содержит заголовок «Что изменить в проекте?», многострочное поле, добавление вложений, кнопку `@` и отправку. Модель показывается компактно; подключение провайдера и расширенные параметры находятся в настройках. Пояснения о лимитах показываются при добавлении файла или ошибке, этапы работы и диагностика — после запуска.

Отправка сначала сохраняет сообщение и запись выполнения. Только после успешной записи начинается платный запрос. Название диалога формируется из первого сообщения без отдельного обязательного платного вызова и доступно для переименования.

Ответ может быть обычным объяснением или планом без изменений файлов. Если нужны изменения, в сообщении ассистента появляется карточка работы с кратким этапом, остановкой и результатом. Подробные события доступны через раскрытие.

### Создание проекта с ИИ

«Новый проект → С ИИ» открывает тот же composer. Название проекта необязательно; тип «Лендинг / Шаблон» можно задать компактным выбором с текущим значением по умолчанию. После отправки создаются проект и первый диалог, затем открывается рабочее пространство.

В диалоге существующего проекта убирается нынешний переключатель создания проекта, заменяющий все файлы. Запрос «создать ещё один лендинг» предлагает создать отдельный проект. Полная замена текущего проекта остаётся отдельным явно обозначенным действием с просмотром удаляемых файлов.

### Изменение выбранного файла

«Изменить с ИИ» открывает новый диалог с упоминанием выбранного файла и ограничением «Только этот файл». Можно приложить изображения, PDF и поддерживаемые текстовые документы, как в текущей файловой доработке. Редактирование изображения использует имеющийся image workflow.

Отдельный FileAi modal после перехода не требуется. Сохраняются существующие гарантии: исходный файл фиксируется на старте, его формат и путь сохраняются, другие файлы и значения не меняются, результат сравнивается с оригиналом перед применением.

В рабочей копии также развивается выбор блоков в preview. Его действие «Изменить выделенное» подключается к тому же диалогу со структурированным block scope, snapshot и locale. Не создавать для него ещё одну отдельную историю; сохранить проверки устаревшего выделения и запрет изменений вне выбранной области.

### Инструменты и уточнения

Planner выбирает source, values или file/image executor. Изменение контента не требует переключать режим; если необходима новая секция или поле, ассистент может менять source и values совместно. Явно заданный scope не расширяется молча: при необходимости ассистент объясняет требуемое расширение задачи.

Во время выполнения сообщение из того же диалога работает как уточнение с отметкой «Будет учтено на следующем шаге». Новый независимый запрос запускается в другом диалоге. В одном диалоге одновременно работает один writer, чтобы сохранить последовательность сообщений. Существующие ограничения steering сохраняются до отдельной доработки.

## Упоминания файлов и вложения

Ввод `@` открывает поиск по относительным путям файлов проекта. Клавиатура: стрелки для выбора, Enter для вставки, Escape для закрытия. Кнопка `@` открывает тот же picker. Упоминание отображается отдельным элементом, который можно удалить или открыть.

Ссылка хранится структурированно: относительный путь, тип файла, hash содержимого и ссылка на snapshot на момент отправки. Снимок позволяет понимать старое сообщение после изменения или удаления файла. Переименование внутри Studio обновляет текущую связь; исторический путь сохраняется. Отсутствующий файл не подменяется другим с похожим названием.

Упоминание передаёт контекст, а ограничение области изменения задаётся отдельно. Текст упомянутого файла передаётся по запросу инструмента в пределах существующих лимитов; упоминание не означает загрузку всех binary assets. Для изображения явно отображается, используется ли оно как вход модели или только как файл проекта.

Вложения показываются компактными карточками с именем, типом, статусом и удалением. Для изображения доступны понятные назначения «Референс» и «Добавить на страницу»; второй вариант добавляет asset только при применении черновика. Paste и drag-and-drop используют ту же проверку, что и upload. Неподдерживаемый формат, превышение размера и неподходящая модель показывают ошибку до provider call.

В первой версии общий composer сохраняет текущие лимиты соответствующих исполнителей. Расширение их возможностей является отдельной задачей; объединение интерфейса само по себе не обещает PDF или image input любой модели. Reference-only вложения остаются вне ZIP для хостинга.

## Данные проекта и диалогов

Ниже предложена схема, а не описание уже реализованных сущностей.

| Сущность | Основные данные | Назначение |
| --- | --- | --- |
| Project | `projectId`, name, kind, `contentRevision`, `metadataRevision`, active binding | Постоянная идентичность и состояние проекта |
| StorageBinding | `bindingId`, `projectId`, type, local handle, display label, persisted revision | Связь проекта с библиотекой или папкой |
| Thread | `threadId`, `projectId`, title, timestamps, archived | Один независимый разговор |
| Message | `messageId`, `threadId`, sequence, role, parts, delivery status | Текст, вложения, упоминания, итог работы |
| Run | `runId`, `threadId`, message, attempt, immutable base snapshot, locale, settings, state | Выполнение одного запроса |
| ChangeSet | `changeSetId`, `runId`, base snapshot/revision, read set, operations, validation, applied revision | Предложенные изменения и результат применения |
| Attachment | `attachmentId`, bytes, mime, name, purpose, content hash | Отдельное хранение вложений с переиспользованием bytes |

`contentRevision` меняется при правках source, folders, values и иной информации, влияющей на результат. Сообщения, названия чатов и progress не меняют эту revision. Иначе любое сообщение сделает все черновики устаревшими.

Для локального Studio каталог, сообщения, runs, changesets и blobs находятся в IndexedDB с индексами по project/thread и versioned migration. Полные binary assets не копируются в каждое сообщение. Базовые snapshots сохраняются до завершения связанных черновиков; удаление не должно лишать pending draft возможности сравнения.

История чатов получает отдельный optional `ConversationPort`. Существующий `ProjectState.history` предназначен для версий и host lifecycle; переиспользовать его для сообщений нельзя. Core сохраняет непрозрачный тип host revision (`string | number`); отдельные числовые счётчики локального Studio не навязываются embedded hosts.

API keys, transport functions и несокращённые provider diagnostics не включаются в проектные данные. Пользовательская история сохраняет запросы, ответы и понятные события инструментов; внутренние planner/reviewer разговоры и reasoning модели не выдаются за историю пользователя. Контекст для следующих сообщений строится из этого диалога, его компактного summary и явно прочитанных файлов. Другие диалоги автоматически не смешиваются.

## Параллельное выполнение

Менеджер выполнения живёт выше переключаемого editor. Компоненты только подписываются на его состояние. Отдельный project session сохраняет host, snapshot и validator, пока есть работа, даже если пользователь открыл другой проект.

Запись checkpoint, применение и продолжение разрешают актуальный storage binding по `projectId`, а не используют захваченный прежний host. После переноса в папку run сохраняет исходную базу для сравнения, но все новые записи маршрутизируются через текущее место хранения. Binding generation исключает позднюю запись в прежнее хранилище.

Предлагаемый стартовый лимит — два одновременных run на приложение с настраиваемым пределом. Лимит учитывает вложенные вызовы writer/reviewer/image и ограничения провайдера. Остальные запросы видимо стоят в очереди; проект не блокируется. Значение лимита уточняется нагрузочными проверками, а не зашивается в UI.

Каждый run владеет своим `AbortController`, model settings, budget, clarification queue и provider lease. `begin`, `finish` и `cancel` адресуются по `runId`; завершение B не освобождает и не отменяет ресурсы A. Изменение настроек влияет на новые запросы, а текущий использует настройки на момент старта.

Нельзя передавать валидатору фонового run callbacks текущего открытого редактора. Он должен проверять snapshot и locale именно этого run. Preview черновика также получает его файлы, а не общий изменяемый `aiDraft`.

В нескольких окнах Studio owner lease и heartbeat исключают одновременное владение одним run. Владение приобретается атомарно; каждый attempt имеет монотонный fencing token. События, checkpoints и финальный результат принимаются только от текущего владельца. Поздние ответы старого владельца игнорируются. Истечение lease не запускает автоматически ещё один платный запрос: зависший attempt сначала помечается interrupted. При наличии Web Locks используется эксклюзивный lock на run. Для коротких локальных записей использовать coordination по проекту и проверку revision в транзакции; [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API) координирует окна одного origin, но не заменяет CAS и не блокирует внешние редакторы папки.

## Просмотр и применение изменений

После генерации сообщение содержит summary, число изменённых файлов/полей и действия «Посмотреть изменения», «Продолжить работу», «Отклонить». Review показывает text diff, before/after для изображений, список удалений и изменения контента. Preview явно подписан «Текущий проект» либо «Черновик диалога …»; выбор черновика не меняет рабочие файлы.

При применении система сравнивает **базу run**, **актуальный проект с несохранёнными правками** и **предложение**. Применяются операции changeset, а не полная замена snapshot.

Для первой поставки достаточно консервативного объединения:

- Изменённый файл не менялся после базы — применить предложение. Правки других файлов остаются.
- Текущий файл уже совпадает с предложением — операция не требует повторной записи.
- Файл изменился и отличается от предложения — показать конфликт. Не выбирать автоматически более новую версию.
- Значения объединять по field path; конкурирующие правки одной величины конфликтуют. Массивы без стабильных IDs считать целиком одной величиной.
- Edit/delete, rename/path collisions, binary replacement и изменения зависимых прочитанных файлов требуют проверки. Если read set устарел, показывать «Контекст проекта изменился» и предлагать обновить черновик.

Автоматический three-way merge непересекающихся диапазонов внутри одного text file можно добавить позже. Он не является условием запуска нескольких диалогов. Даже изменения разных файлов могут противоречить друг другу через schema/includes/values; после объединения обязательно повторно проверить весь проект парсером, analyzer и renderer.

Read set включает значимый контекст всех stages, включая переданные planner/reviewer source, schema и values, а не только вызовы `read_file`. Устаревший контекст требует обновления черновика либо явного просмотра и подтверждения заново проверенного объединённого кандидата. Пользователь видит итоговый diff к актуальному проекту; старый preview не является основанием для подтверждения нового кандидата.

Коммит сериализуется только на время применения к конкретному проекту. Долгая генерация этот lock не держит. Валидировать можно до короткого commit, затем повторно проверять revision; при новой правке пересчитать кандидат или остановиться с конфликтом. Предложение и сообщения сохраняются при любой ошибке.

Для несохранённого editor buffer отдельно фиксируется `workingVersion` и hash working snapshot. Проверка только persisted revision недостаточна: ручная правка могла появиться во время валидации, но ещё не попасть в autosave. Перед commit проверяются обе версии и in-flight autosave через общий координатор команд проекта; последующие правки не заменяются возвращённым saved snapshot и остаются pending. Повторное Apply идемпотентно по `changeSetId` и не создаёт два коммита.

Library commit подтверждает новую revision и applied state в одной транзакции проектного репозитория. Folder commit использует журнал операций и сохранённую recovery copy: последовательные записи разных файлов не являются общей транзакцией. Статус «Применено» появляется после завершения и проверки записи; при частичном сбое доступен recovery, а не ложный успех. Undo создаёт новую проверенную revision и также учитывает последующие ручные изменения.

## Перенос в локальную папку

Вместо `Project folders` появляется «Хранение проекта» с состояниями «На этом устройстве», «Сохранено в папке …», «Нужен доступ к папке», «Есть внешние изменения». Рядом указано последнее успешное сохранение. Необязательная подпись места доступна в деталях и не выглядит как поле выбора фактического пути.

Сценарий: проект создан с ИИ → «Хранение проекта → Сохранить в папку…» → системный выбор папки → сохранение → продолжение того же проекта. Количество проектов, `projectId`, диалоги и pending drafts сохраняются.

Порядок переноса:

1. Вызвать системный выбор папки непосредственно из действия пользователя, затем проверить доступ. Пустая папка — основной сценарий. Для непустой показать найденный проект либо конкретные пересечения файлов; не заменять чужие файлы автоматически. Отмена ничего не меняет.
2. После выбора зафиксировать content revision и сделать recovery snapshot. Если есть активные runs, checkpoint сохраняется; их base snapshots не меняются. До первой записи исходное состояние и журнал переноса должны быть сохранены.
3. Записать source, assets, folders, values и метаданные. Проверить результат. Пока запись не подтверждена, прежнее хранение остаётся активным.
4. Под коротким lock сверить content и metadata revisions; догнать изменения, появившиеся за время копирования. Успех переключает binding без нового проекта; ошибка или отмена оставляет проект доступным в Studio.
5. Сохранить связь каталога с папкой. Локальный cache служит восстановлению, а не второй записью в списке проектов. Автосохранение сообщает успех только после записи в активное место хранения.

На диске предлагаются служебные данные `.trafficops/project.json` с version/projectId/kind/revisions, существующий `.trafficops/values.json`, `.trafficops/conversations.json` и каталог вложений/черновиков. Точный layout утверждается в ADR до реализации; допустима нормализованная структура вместо одного большого JSON. Метаданные записываются с schema validation и лимитами, отдельно от файлов лендинга.

Для активного folder binding отдельно подтверждается `metadataRevision`: новые сообщения, вложения и checkpoints тоже записываются в папку. Статус полностью сохранённого проекта требует подтверждения content и metadata. При недоступной папке данные сохраняются в recovery на устройстве, а UI сообщает, что папка ещё не обновлена. Служебные файлы не входят в authoring tree и source manifest для модели.

Portable snapshot имеет hash содержимого и ссылку на базу. Равенство номеров revision из разных копий или устройств не доказывает равенство source/values. Restore и reconnect сравнивают содержимое; сам по себе одинаковый ID не разрешает перезапись.

При открытии папки `projectId` сначала читается из metadata. Уже известный проект переподключается; неизвестный добавляется в единый каталог. Одинаковый ID и отличающийся snapshot не дают молчаливого объединения: доступны «Продолжить этот проект» с просмотром различий или «Создать копию». Скопированная папка не считается автоматически тем же активным binding. Копия получает новый ID и remapping thread/run IDs; импортированные активные runs становятся interrupted.

Папка без metadata открывается как legacy проект и получает identity после успешной записи. Пустая папка при открытии не получает starter автоматически: запись стартовых файлов происходит только после явного создания проекта. Потеря разрешения сохраняет правки и историю в recovery того же projectId. «Переподключить папку» не создаёт второй проект. «Отключить папку» означает удалить подключение из Studio, а не удалить файлы с компьютера; перед этим предлагается оставить локальную копию того же проекта.

Handles можно хранить в IndexedDB; permission необходимо проверять при доступе и восстанавливать через явное действие пользователя. В Chrome установленные приложения получают persistent permissions после выдачи доступа, однако отзыв разрешения остаётся возможным. См. [File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access) и [persistent permissions](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api). API доступен не во всех окружениях; при отсутствии доступа предлагается переносимый ZIP.

[showDirectoryPicker требует transient user activation](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker). Длительные сохранения до вызова picker могут её потерять; подготовку переноса нужно завершать после выбора либо до отдельного явного нажатия выбора папки.

## Экспорт и импорт

| Пункт одного меню «Экспорт» | Содержимое | Для чего |
| --- | --- | --- |
| Лендинг для хостинга | Generated HTML и assets проекта | Разместить готовую страницу |
| Проект Studio | Source, assets, folders, values, identity и выбранная история/черновики/вложения | Продолжить редактирование и перенести проект |

У переносимого проекта история и завершённые черновики включены по умолчанию; можно явно отключить историю и связанные референсы. Пользователь видит состав архива перед скачиванием. Отсутствие истории не меняет identity. Credentials, directory handles, абсолютные path labels и transport diagnostics не экспортируются. В ZIP для хостинга служебная `.trafficops` информация не включается.

Экспорт использует фиксированный актуальный snapshot. Running files и неполные streamed strings не попадают в архив; завершённый checkpoint сохраняется, а run после импорта имеет interrupted status. Лимиты импорта и защита от traversal, symlinks, hidden files и ZIP bombs сохраняются. Для новых служебных путей вводится точный allowlist и ограниченная schema; нельзя просто разрешить все hidden paths. История учитывается в общем бюджете архива, превышение показывает понятный выбор состава, а не незаметное удаление сообщений.

ZIP с identity предлагает «Продолжить проект» или «Создать копию», если этот ID уже известен. Продолжение требует проверки revision и различий, чтобы старый backup не перезаписал новые данные. На другом устройстве неизвестный ID сохраняется. Старый ZIP без identity создаёт новый проект с явно выбранным типом; существующие архивы остаются совместимыми.

«Сохранить в папку» не находится среди форматов экспорта: это смена активного хранения, после которой можно работать дальше без повторного импорта.

## PWA и встроенный редактор

В shared shell вводится явная presentation policy: app layout, embedded layout и при необходимости расширение embedded. Studio PWA использует app layout постоянно, с обычной доступной структурой страницы вместо dialog/popover и focus trap на весь editor.

В PWA отсутствуют «Свернуть редактор» и «Развернуть редактор». Escape закрывает текущий picker/menu/modal, но не уменьшает рабочее пространство. Versions открывается внутри workspace. Панели файлов и preview можно скрыть понятными локальными действиями. Системное сворачивание окна ОС остаётся обычным поведением приложения.

Встроенный `HttpHost` сохраняет текущие expand/collapse и host-owned policies. Добавление thread capability должно быть опциональным: существующие consumers не обязаны немедленно поддержать новый репозиторий диалогов. Провести versioning контрактов и conformance checks, не включать новые Studio возможности автоматически у других hosts.

## Восстановление и обновления

Сообщения и изменения состояния сохраняются по project/thread/run. Старый единственный workspace slot `last` заменяется project-keyed recovery. После reload queued/running attempt с потерянным owner становится interrupted; ни генерация текста, ни изображения не повторяются автоматически. Пользователь явно продолжает работу, сохраняя готовые результаты.

Переход между диалогами и проектами при открытом приложении не прерывает run. Полная работа после закрытия окна не обещается: service worker не гарантирует выполнение долгого запроса. Это ограничение описано в [MDN о фоновой работе PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation). Для такого требования позднее потребуется серверный runner или desktop runtime.

Обновление приложения сначала сохраняет сообщения, правки и checkpoints. При active runs предлагается дождаться завершения или остановить и обновить с сохранением черновиков. Готовый неприменённый changeset сам по себе обновление и навигацию не блокирует.

Migration старых данных переносит Library IDs без изменения, directory записи — в bindings, creation brief — в первый диалог, recovery — в восстановленный run. Из prompt, clarifications и summary восстанавливаются только реально сохранённые сообщения; отсутствующая старая история не выдумывается. Старые записи удаляются после подтверждённой миграции. Совпадение имён или файлов не является достаточным основанием автоматически склеить legacy проекты.

Migration хранит журнал и стабильное соответствие legacy record → project/thread/run IDs. Повтор после закрытия или сбоя продолжает перенос с теми же IDs. Миграция между несколькими IndexedDB databases не является одной общей транзакцией; удаление legacy данных выполняется только после readback нового состояния.

## Этапы реализации

Оценки предварительные, для одного разработчика, знакомого с кодом. Они включают целевые проверки и не являются сроком выпуска. До начала этапов следует отдельно зафиксировать текущие незакоммиченные AI/file изменения, чтобы новая работа опиралась на согласованную базу.

| Этап | Результат и основные места изменения | Зависимость | Оценка |
| --- | --- | --- | --- |
| 1. Понятные действия и постоянный PWA экран | Presentation policy в `EditorShell`, исправление Escape/Versions, группировка `ProjectSidebar`, одно меню экспорта, понятные подписи хранения | Можно делать независимо | 2–3 дня |
| 2. Identity и репозиторий диалогов | ADR/schema, Project/Binding/Thread/Message/Run/ChangeSet, separate revisions, миграция Library/recovery, optional ports в core | База для последующих этапов | 4–6 дней |
| 3. Общий composer и история | `ConversationPanel`, `ThreadList`, `Composer`, `FileMentionPicker`, общие attachments; новый проект и file action используют диалог; обычные ответы без обязательных изменений | Этап 2 | 4–6 дней |
| 4. Независимые runs и безопасное применение | App/session manager, адресный AI port, queue, snapshot validator, отдельный draft preview, patch/CAS/conflicts и recovery folder commit; удалить AI из общего lock | Этапы 2 и 3; apply должен быть готов до снятия блокировок | 5–8 дней |
| 5. Перенос проекта | Save to folder, identity на диске, история/черновики в folder и ZIP, restore/copy, reconnect того же проекта | Этапы 2 и 4 | 4–6 дней |
| 6. Проверка сценариев и документация | Reload/multi-window/permission/limits/embedded regression, доступность, README/PRODUCTION_CHECKS | Все этапы | 2–3 дня |

Итого ориентировочно 21–32 рабочих дня. Главные неопределённости — восстановление частичной записи папки, миграция раздельных хранилищ и расширение общего host contract. Полноценный text merge и облачные функции оцениваются отдельно.

Минимальная полезная поставка после этапа 4: несколько постоянных диалогов, единый composer с `@`, параллельные черновики и работающий ручной editor. Полная поставка включает этап 5: проект можно перенести в папку без дубля и потери истории.

## Критерии приёмки

1. В проекте созданы два диалога: A меняет оформление, B — контент. Оба генерируют независимо; пользователь вручную редактирует файл, autosave продолжается.
2. Пользователь открывает другой диалог и другой проект. A и B продолжают работу; их сообщения и результаты остаются у исходного проекта. Validator и locale не переключаются вслед за экраном.
3. Остановка B не отменяет A. Ограничение concurrency показывает очередь, не блокирует editor. Два окна не исполняют один run дважды.
4. A и B изменили независимые файлы/поля: последовательное применение сохраняет оба результата и ручные изменения. Общие schema/dependency ошибки выявляются до commit.
5. Два результата или ручная правка затрагивают один файл: применение показывает конфликт и ничего не перезаписывает молча. Edit/delete, rename, arrays и raster конфликтуют безопасно.
6. Preview черновика не становится содержимым current project. Apply failure, quota error или потеря доступа к папке сохраняет предложение и не показывает «Применено».
7. После reload восстанавливаются несколько диалогов, сообщения, вложения и завершённые checkpoints. Незавершённые runs отмечены interrupted; provider calls автоматически не повторяются.
8. Новый AI проект создаётся из компактного composer; повторное открытие не повторяет paid generation. File action создаёт диалог с file scope; ограничение действительно соблюдается.
9. `@` работает мышью и клавиатурой. Rename/delete не ломает чтение старого сообщения; missing file отображается явно. Вложения проходят существующую проверку до отправки.
10. AI проект → «Сохранить в папку» → reopen: тот же ID, то же количество проектов и вся история. Отмена, denied permission и частичный сбой не оставляют ложный успешный перенос.
11. Повторное открытие известной папки переподключает проект. ZIP round-trip сохраняет kind/identity/history; старый backup не перезаписывает новые изменения без просмотра. Копия получает новую identity.
12. Один экспорт объясняет оба назначения. Hosting ZIP содержит только output/assets; Studio ZIP содержит выбранные переносимые данные, без ключей и handles. Старые ZIP продолжают импортироваться.
13. PWA не сворачивает editor по Escape, кнопке или переходу в Versions. Embedded editor сохраняет expand/collapse, host restrictions и preview behavior.
14. Проверены keyboard/focus, подписи и responsive layout: действия доступны без hover, длинные названия/пути и ошибки не перекрывают composer.
15. Ручная правка во время final validation и незавершённый autosave инвалидируют устаревший apply candidate. Поздний ответ старого run owner не меняет новый attempt.
16. Apply run после переноса записывает в актуальную папку. Новое сообщение и reopen подтверждают сохранение истории, а открытие пустой папки не пишет starter без явного действия.
17. Reload между записью новых migration records и удалением legacy данных не создаёт дополнительных threads/runs и не повторяет paid requests.

Для реализации использовать существующие suites `hosts`, `studio-library`, `directory-projects`, recovery, file AI, attachments, image generation, PWA ports и embedded consumer. Добавить проверки persistence/concurrency/merge/transfer для новых гарантий. Платные provider smoke checks не нужны для проверки маршрутизации, хранения и конфликтов: эти сценарии покрываются управляемыми ответами и faults.

Проверки изменений включают `npm run test --workspace @trafficops/template-studio`, тесты shared shell, `npm run check --workspace @trafficops/template-studio`, production build и целевые browser сценарии. В рамках этого планирования application code не изменялся и эти suites не запускались.
